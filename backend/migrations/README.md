# Миграции базы данных

## Что здесь лежит

| Файл | Что делает |
|---|---|
| `001_schema.sql` | Полная структура базы: 47 таблиц, 105 индексов, 104 внешних ключа, 6 последовательностей |
| `002_seed_achievement_categories.sql` | Справочник категорий достижений (8 строк) — настроечные данные |
| `003_consents.sql` | Согласия по 152-ФЗ: редакции текстов, кто за кого подтвердил, журнал |
| `004_consent_documents.sql` | Тексты трёх согласий, редакция «1.0-черновик» |
| `005_club_staff.sql` | Должности сотрудников в КЮДе; club_coordinators становится представлением |
| `006_teams.sql` | Команды клубов на форумы и выезды |

Снято с рабочей базы `db_dod_platform_clean` (PostgreSQL 17) через Adminer
10 сентября 2026 года.

## Как поднять базу с нуля

```bash
psql "$DATABASE_URL" -f backend/migrations/001_schema.sql
psql "$DATABASE_URL" -f backend/migrations/002_seed_achievement_categories.sql
psql "$DATABASE_URL" -f backend/migrations/003_consents.sql
psql "$DATABASE_URL" -f backend/migrations/004_consent_documents.sql
psql "$DATABASE_URL" -f backend/migrations/005_club_staff.sql
psql "$DATABASE_URL" -f backend/migrations/006_teams.sql
```

## ⚠️ Про 004: тексты согласий — черновик

Редакция называется `1.0-черновик` намеренно. Тексты составлены по
требованиям статьи 9 152-ФЗ, но **не проверены юристом**. Название версии
видно и в интерфейсе, и в журнале согласий: если согласие всё же будет
дано против черновика, это останется видно в записи.

После проверки юристом публикуется редакция `1.0` — через интерфейс
администратора либо `POST /api/consent-documents`. Старая редакция
остаётся в базе навсегда: на неё ссылаются уже данные согласия.

На RelaxDev то же самое делается через панель: проект → «База данных» →
«Восстановить из файлов», файлы загружаются по порядку сверху вниз.

## ⚠️ Данные сюда не кладём

В базе хранятся персональные данные несовершеннолетних участников и их
родителей: ФИО, даты рождения, школы, телефоны, адреса электронной почты,
а также хеши паролей. Такому не место в репозитории — ни в приватном,
ни тем более в публичном.

Экспорт из Adminer по умолчанию выгружает **структуру вместе с данными**.
Чтобы получить только структуру, на странице Export выставьте:

- **Output** → `save`
- **Format** → `SQL`
- **Tables** → `CREATE`
- **Data** → оставить **пустым**

Файлы вида `db_*.sql` и `*dump*.sql` добавлены в `.gitignore` — на случай,
если дамп с данными случайно окажется в этой папке.

## Как обновлять

При изменении структуры базы снимайте новый дамп и добавляйте **новый**
пронумерованный файл (`003_...sql`), а не правьте старые: применённые
миграции должны оставаться неизменными, иначе на другом окружении
получится другая база.

## 007_parent_invitations.sql

Приглашения родителей. Выполнять после 006.

**Что делает.** Создаёт таблицу `parent_invitations`: одно приглашение —
одна строка, токен хранится только как SHA-256.

**Зачем.** Раньше родитель привязывал ребёнка, вводя пароль ребёнка.
Так семья приучается жить под одной учётной записью, и тогда запись
«согласие дал законный представитель» перестаёт что-либо значить — а
ради неё весь раздел согласий и существует. Теперь приглашение
выпускает руководитель КЮДа из карточки участника либо сам участник
(коротким кодом), а родитель заводит собственный пароль.

**После применения** проверить:

```sql
SELECT COUNT(*) FROM parent_invitations;            -- 0, таблица пустая
SELECT indexname FROM pg_indexes
 WHERE tablename = 'parent_invitations';            -- три индекса
```

Старый маршрут `POST /api/parent-link-child` отвечает 410 с объяснением:
он оставлен только ради открытых вкладок в браузерах.

## 008_club_sessions.sql

Занятия КЮДа и посещаемость. Выполнять после 007.

**Что делает.** Создаёт две таблицы: `club_sessions` (занятие клуба —
дата, тема, место, кто провёл, состояние) и `session_attendance`
(отметка присутствия: один участник — одна отметка на занятии).

**Зачем.** Платформа была нужна несколько раз в год: форум, отчёт, ещё
форум. Клуб собирается еженедельно, и эта работа нигде не отражалась —
отчёт за месяц писался по памяти, а то, что участник перестал ходить,
выяснялось в конце года.

**Почему четыре статуса, а не галочка.** «Прогулял» и «болел» — разные
разговоры с родителем. С галочкой руководитель начнёт дописывать причину
в комментарий, и посчитать что-либо станет невозможно.

**После применения** проверить:

```sql
SELECT COUNT(*) FROM club_sessions;      -- 0
SELECT COUNT(*) FROM session_attendance; -- 0
```

Отменённое занятие не может остаться без причины, а удалить занятие с
отметками нельзя — это ограничения на уровне базы и сервера, а не
пожелание интерфейса.

## 009_club_membership.sql

Один источник состава клуба. Выполнять после 008.

**Что было не так.** Состав хранился в двух местах: поле `users.club_id`
и таблица `club_participants`. При переводе участника в другой клуб поле
обновлялось, а в таблицу добавлялась ещё одна строка — прежняя
оставалась активной. Человек начинал числиться сразу в двух клубах.

Видно было так: в списке КЮДов у Владивостока шесть участников, а в
журнале занятий и в отчёте — три. Три из шести давно перешли в другие
клубы.

**Почему это опаснее, чем выглядит.** Лист посещаемости, приглашения
родителям и подсчёт для отчёта берут состав из `users.club_id`, а
счётчик в списке клубов брал его из `club_participants`. Пока числа
расходятся, руководитель не может доверять ни одному из них.

**Что делает миграция.** Добавляет `left_at`, закрывает записи,
разошедшиеся с действительностью, и заводит недостающие. Дальше
`users.club_id` — единственный источник истины, а `club_participants`
остаётся историей членства: когда пришёл и когда ушёл.

**После применения** проверить, что расхождений не осталось:

```sql
SELECT COUNT(*) FROM club_participants cp
 WHERE cp.status = 'active'
   AND NOT EXISTS (SELECT 1 FROM users u
                    WHERE u.id = cp.profile_id AND u.club_id = cp.club_id);
```

Должно вернуть 0. И сверить счётчик в списке КЮДов с числом в журнале
занятий того же клуба — теперь они считаются из одного места.

## 010_user_deletion.sql

Удаление пользователя. Выполнять после 009.

**Что было не так.** Удалить пользователя было нельзя: десять внешних
ключей ссылались на `users(id)` без правила `ON DELETE`, а это значит
«запретить удаление». Сервер получал отказ от базы, ловил его общим
обработчиком и отвечал «Внутренняя ошибка сервера» — человек видел
поломку там, где сработало ограничение целостности.

**Что делает.** Девять ключей авторства переводит на `SET NULL`:
мероприятие, достижение или новость остаются, а поле «кто создал»
становится пустым. Ровно так уже вёл себя журнал действий. Десятый —
`announcements.created_by` — объявлен NOT NULL, обнулить нельзя,
поэтому объявления удаляются вместе с автором.

**Зачем это нужно по существу.** По 152-ФЗ отзыв согласия влечёт
уничтожение персональных данных. Если удалить участника физически
невозможно, выполнять это требование нечем.

**После применения** проверить, что ключей без правила не осталось:

```sql
SELECT conrelid::regclass AS таблица, conname AS ключ
  FROM pg_constraint
 WHERE confrelid = 'users'::regclass AND contype = 'f' AND confdeltype = 'a';
```

Пустой результат — всё в порядке (`a` означает «запретить удаление»).
